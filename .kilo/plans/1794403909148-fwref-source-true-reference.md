# Plan: Source-true firmware reference for Instrument and Master

## Goal

Replace the hand-drawn emulator reference for Instrument General and Master 1/3 with a reference that is
generated by the firmware's own NewDisplay control code and locked to the CE source in `core/`.

The app must then be ported to that reference. A high pixel score is meaningless if the reference is wrong.

## Non-negotiable rule

**Do not hand-draw the new reference.** If the firmware control code cannot be executed on the host, stop and
report the blocker. Do not fall back to copying coordinates and colors from the source into another drawing
function. The only acceptable fallback is a checked-in, real 800x480 firmware capture, and only if the user
provides one.

## Why the current reference is not trustworthy

The current reference was written by approximating screenshots, not by executing firmware logic:

- `native/tools/display_emulator/FT812ScreensExtra.cpp:11-55` draws 24x260 green bars, top headers, green
  filter boxes, and "Overdrive" text. Firmware draws 75px-wide white fills, no headers, a `cList`, and "More"
  (`core/interface/instrumentEditor/gInstrEdit.cpp:151-197,792-937`,
  `core/libs/NewDisplay/bar.cpp:88-270`, `core/source/Themes.cpp:43-180`).
- `native/tools/display_emulator/FT812ScreensCore.cpp:184-219` draws green VU fills, green underlines, and
  white track names. Firmware Master 1/3 has no green, labels are grey `#777777`, values are white, and there
  are no underlines (`core/interface/masterParams/gMasterParams.cpp:253-358`,
  `core/libs/NewDisplay/bgLabel.cpp:83-140`).
- The app was then matched to those approximations (`native/app/views/InstrumentBars.cpp:20-158`,
  `native/app/views/MixerView.cpp:137+`), so existing parity scores measure the wrong target.

## Truth chain

The reference is accepted only if all four layers pass:

1. **Executable provenance** - the image is rendered by unmodified firmware control sources:
   `bar.cpp`, `label.cpp`, `list.cpp`, `frame.cpp`, `bgLabel.cpp`, `displayControls.cpp`.
2. **Generated layout provenance** - every control property is evaluated from a source expression or
   verified against a hashed source range. No manual coordinate entry.
3. **Independent image assertions** - a separate checker inspects the PNG and asserts firmware facts
   (white fill width, no green pixels in Instrument/Master, label colors, list geometry, etc.).
4. **Hardware evidence** - user photos/video frames are used as a low-frequency structural check, not as a
   pixel-perfect oracle.

Any failure stops the pipeline.

### 1.2 Provide narrow host shims (no drawing logic)

Add under `native/tools/fwref/shim/`:

- `display_stub.cpp` - define the global `cDisplay display;`, a constructor that points `theme` at a mutable
  copy of `themeDefault`, plus `displayFontCount`, `fonts[]`, `bitmaps[]`, and `displayBitmapsCount` (the
  latter two can be empty for these screens).
- `fonts.cpp` - decode the five firmware fonts with the existing `decompress()` path, using the same
  metadata offsets as `core/libs/NewDisplay/display.cpp:236-266`.
- `Tracker.h` / `platform_stub.cpp` - satisfy `list.cpp`'s `Tracker::getInstance()->getPlatform()->getTimer()
  ->millis()` call. Return a fixed timestamp.
- `log.h` - empty logging macros if needed by `displayControls.cpp`.

Shims may replace platform services. They must not replace drawing, layout, color, or font logic.

### 1.3 Implement the FT812 API subset

Implement the `API_*` functions declared by `core/libs/FT812/FT812.h` as immediate-mode calls into
`FT812DisplayEmulator`:

- `API_COLOR`, `API_LINE_WIDTH`, `API_BEGIN`, `API_END`, `API_VERTEX2F`, `API_VERTEX2II`
- `API_SAVE_CONTEXT`, `API_RESTORE_CONTEXT`, `API_SCISSOR_XY`, `API_SCISSOR_SIZE`
- `API_BLEND_FUNC` (`SRC_ALPHA/ONE_MINUS_SRC_ALPHA`, `SRC_ALPHA/ZERO`)
- `API_CMD_GRADIENT` (horizontal and vertical; interpolate within the active scissor)
- `API_CMD_TEXT` (`OPT_CENTERX`, `OPT_CENTERY`, `OPT_RIGHTX`)
- `API_POINT_SIZE` and `API_BEGIN(FTPOINTS)` for the "More" dots
- No-op display-list lifecycle functions (`DLSTART`, `CLEAR`, `DISPLAY`, `SWAP`, etc.)

Rules:

- `RECTS` is a filled rectangle. `LINE_STRIP`/`LINES` use the current line width. `LINE_WIDTH` is in
  1/16 px (`16` = 1px, `24` = 1.5px).
- Text uses the emulator's decoded L4 bitmaps. Add the two missing firmware fonts.
- Fix the font index mapping to the firmware table order:
  `0=Light14`, `1=Light17`, `2=Regular14`, `3=Bold17`, `4=Regular12`.
  The current enum only has three fonts and the wrong order.
- Implement scissor clipping for every primitive.

### 1.4 Oracle self-test

Add `fwref_selftest` (Catch2 test or small executable) that creates a `cBar` with the firmware properties:
`x=1, y=29, w=97, h=394`, `value=50`, active colors, background + gradient + bottom shadow. Render it and assert:

- background `#0A0A0A` at `(2,30)`
- container `#080808` at `(12,41)`
- white fill `#FFFFFF` in the lower half of the container (75px wide, ~184px high)
- no green pixels

**Gate:** do not write any screen reference until this test passes. If it fails, fix the shim/API, not the
expected values.

## Phase 2 - Generate the layout spec from source

Add `native/tools/fwref/specs/` and `native/tools/fwref/extract_spec.py`.

The spec is data, not drawing code. Each entry must contain:

- control type (`cBar`, `cLabel`, `cList`, `cFrame`, `cBgLabel`)
- source file and line range
- SHA-256 of those exact source lines
- property expressions copied verbatim from source (e.g. `"(800 / 8) * (4) + 1"`, `"29"`, `"800 / 8 - 3"`,
  `"394"`)
- symbolic style names from `commonControls.h`
- color source (theme field + index, e.g. `activeBarColors[0]`)
- text expression / scenario key
- creation order index

`extract_spec.py` must:

1. Parse the known layout tables and property blocks in `gInstrEdit.cpp` and `gMasterParams.cpp`.
2. Evaluate only arithmetic expressions; reject anything else.
3. Resolve theme colors by parsing the default `Theme` object in `core/source/Themes.cpp:43-180`.
4. Fail if a cited line range no longer matches its recorded hash or if an expected expression is absent.
5. Emit `specs/instrument_general.json`, `specs/master_page1.json`, `specs/chrome.json`.

If a construct cannot be parsed, stop and add a parser rule. Do not hand-copy the number.

## Phase 4 - Verification gates

Add `native/tools/fwref/check_reference.py` and tests.

1. **Spec lock** - `verify_spec.py` re-extracts the source, recomputes hashes, and fails on any drift.
2. **Determinism** - render twice; require byte-identical PNGs.
3. **Manifest** - `reference_manifest.json` must match the checked-in PNG hashes and source hashes.
4. **Image assertions** - independently inspect the PNG:
   - Instrument: no pixels with `g > r+16 && g > b+16` inside the workspace (no green).
   - Instrument: bar 0 fill is white, 75px wide, starts at `y = 29+10+184` for value 50.
   - Instrument: filter list selected frame is white, not green.
   - Master: volume fill is white and ~81% high; columns 1-4 are flat `#0A0A0A`.
   - Bottom bar: no green underline; separators at x=100i; label text color `#777777`.
5. **Negative control** - a test perturbs one spec value (e.g. bar color to green) and requires the checker
   to fail. This proves the gate is real.
6. **Hardware evidence** - rectify/crop the user photos or video frames and compare region masks
   (bar presence, white/green, label positions). Record the result in
   `native/tools/fwref/evidence/README.md`. Do not use this as the pixel metric.

Only after all six pass is the reference considered true.

Acceptance:

- All `fwref` gates pass.
- Instrument and Master comparison scores are measured against the new reference, not the old one.
- No green pixels in the Instrument/Master workspace or bottom bar.
- Remaining differences are limited to known text rasterization and are documented, not hidden.
- If a score drops, inspect whether the app or the reference is wrong; do not adjust the reference to raise
  the score.

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| Core control code does not compile on host | Add only platform shims; never copy drawing logic. Report if blocked. |
| EVE primitive semantics differ | Oracle self-test plus negative control; validate against photos. |
| Text placement is approximate | Use firmware L4 fonts and `CMD_TEXT` options; treat glyph raster as known residual. |
| Scenario differs between app and reference | One `scenario.json`; a test asserts app state equals it before comparison. |
| Bottom-bar changes affect other screens | Scope the renderer change to Instrument/Master first; audit other screens after. |
| Spec parser misses a construct | Fail closed; add a parser rule; never hand-copy the value. |

## Out of scope

- Re-baselining the other seven screens (same pipeline can follow).
- Switching the app from TTF text to L4 glyph bitmaps (known residual gap).
- Audio/DSP behavior changes; this is a visual parity task.

## Definition of done

- `fwref` renders Instrument and Master 1/3 from unmodified firmware control code.
- Spec, source hashes, PNG hashes, and deterministic regeneration all pass.
- Independent image assertions and the negative control pass.
- Hand-drawn Instrument/Master reference code is removed.
- The app Instrument General and Master 1/3 match the new reference structurally and textually.
- Full test suite and functional smoke pass; comparison artifacts are regenerated.
